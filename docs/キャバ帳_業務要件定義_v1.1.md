## 0. 本書のスコープと前提

- 本書は **業務要件（何を実現するか）** を定義する。システム設計（アーキテクチャ・技術選定・データ物理設計）はv1.0第2部および別途システム化要件定義に委ねる。
- **未決の前提**：実装プラットフォーム（React PWA / iOSネイティブ）は本書時点で未確定。本書の業務要件はプラットフォーム非依存で記述する。
- 本書で追加する機能ID：**F-12（顧客ランク体系）／F-13（向き不向き登録）／F-14（占い・相性診断）**。既存のF-01〜F-11はv1.0を踏襲する。
- 追加3機能に共通する業務目的：**「誰を、どの熱量で、どう扱うか」の判断をキャスト本人が言語化・記録し、日々の接客とLINE営業の質を安定させること。**

## 1. 追加要件の背景と目的

### 1.1 背景
キャストは顧客ごとに「太客か見込みか」「気が合うか」「今日は何に気をつけるべきか」を**感覚で判断**しており、体調や気分で接客の質がぶれる。また新人・移籍時に顧客の温度感が引き継げず、太客化のチャンスを逃す。占い・相性は水商売の会話フックとして日常的に使われるが、記録・再利用されていない。

### 1.2 目的（追加分）
| # | 目的 | 対応する成果指標（KPI） |
|---|---|---|
| G4 | 顧客を熱量・役割で区分し、営業リソースの配分を最適化する | ランク別の指名転換率・離脱率 |
| G5 | 相性と注意点を可視化し、接客・返信の失敗（地雷）を減らす | 「注意点」参照後の顧客離脱率の低下 |
| G6 | 占いを会話フック兼セルフケアの材料として資産化する | 占い起点の連絡実施率・返信率 |

### 1.3 利用者
一次ユーザーはキャスト本人のみ（v1.0を踏襲）。顧客（データ主体）は本機能に直接触れない。ランク・向き不向き・相性はいずれも**ユーザー本人の主観的評価**であり、他者に共有されない。

## 2. F-12 顧客ランク体系（顧客レベル区分）

### 2.1 目的
顧客を「売上上の役割」と「感情上の役割」で分類し、営業の優先度と接し方を明確化する。既存の`tags`（VIP/新規/要注意/太客）を、排他的な**単一ランク**へ格上げして体系化する。

### 2.2 ランク定義
| コード | 呼称 | 定義（業務上の意味） | 主な営業方針 |
|---|---|---|---|
| **VVIP** | 1番の太客 | 売上最上位。指名・同伴・場内の中心。失うと売上に直撃 | 関係維持を最優先。特別感の演出、記念日対応を手厚く |
| **VIP** | 定期的な太客 | 安定して高額利用する常連。月内に複数回来店 | 来店リズムの維持。飽きさせない話題供給 |
| **IP** | 見込み客 | 太客化が期待できる新規〜育成中。単価/頻度は発展途上 | 接触頻度を上げ、次回来店の確約を取りにいく |
| **LOVE** | スキピ（好きピ） | キャスト自身が個人的に好意を持つ客。売上と切り離れる場合あり | 営業と私情の線引きを意識。感情移入の自己管理 |
| **BADBOY** | 痛客（バッドボーイ） | トラブル・精神的負担・売掛/危険リスクが大きい要注意客 | 距離を保つ。深追いしない。必要に応じ黒服相談 |

### 2.3 業務ルール
- ランクは**1顧客につき1つ**（排他）。ただし補助的な`tags`（新規・誕生日近い 等）は従来通り複数付与可。
- ランクは**手動設定を基本**とし、システムは**推奨ランクを提案**する（確定はユーザー）。
  - 推奨ロジック例：累計売上・来店頻度の上位帯 → VVIP/VIP候補、来店1〜2回かつ単価未確定 → IP候補、リスクスコア70点以上（v1.0 F-02）→ BADBOY候補。
  - LOVE（スキピ）は感情要素のため**自動提案しない**（手動のみ）。
- ランク変更は履歴（いつ・どのランクから）を残す。降格（VVIP→VIP等）はKPI分析の重要シグナル。
- ランクは既存機能に波及する：
  - **F-07 特別連絡レコメンド**：VVIP/VIP/LOVEを優先、BADBOYは非営業連絡の推奨対象から除外。
  - **F-06 返信案生成**：ランクに応じてトーン（VVIP=丁寧×特別感 / IP=距離を詰める / BADBOY=事務的・境界線重視）を切替。
  - **F-09 売上レポート**：ランク別の人数構成・売上構成・転換率（IP→VIP等）を可視化。

## 3. F-13 向き不向き登録（相性メモ）

### 3.1 目的
顧客ごとに「自分と**合う/合わない**」をキャスト本人が自己評価して登録し、接客前に確認できるようにする。占い（F-14）が生年月日ベースの客観指標なのに対し、F-13は**実接客に基づく主観評価**を担う。

### 3.2 機能要件
- 顧客詳細に「向き不向き」セクションを設け、以下を登録する。
  - **相性区分**：`得意`（向いている）／`普通`／`苦手`（向いていない）の3段階（将来5段階拡張可）。
  - **理由タグ（複数選択）**：会話が弾む／聞き役が向く／テンションが合う／下ネタ耐性／説教されがち／束縛が強い／マウント傾向／金払いは良いが疲れる 等（マスタから選択＋自由記述）。
  - **自分の消耗度**：接客後の疲労感を3段階で記録（セルフケア機能と連動）。
- 一覧画面で「得意な客」「苦手な客」でフィルタ可能。出勤前に**苦手客の来店予定があれば注意表示**。
- 向き不向きは**ランク（F-12）と独立**（例：VVIPだが「苦手」＝重要だが気を張る客、という状態を表現できる）。この掛け合わせが接客戦略の要になる。

### 3.3 ランク×向き不向きの接客サマリ
顧客詳細に、ランクと向き不向きを掛け合わせた**一言サマリ**を自動表示する。
| ランク＼相性 | 得意 | 苦手 |
|---|---|---|
| VVIP | 最強の関係。維持最優先で自然体を活かす | 売上の要だが消耗大。事前準備と回復をセットで |
| VIP | 安定株。会話の型を再現し飽きさせない | 距離感を固定化し、無理に踏み込まない |
| IP | 太客化の最有力。接触頻度を上げる | 育成対象だが優先度は下げてよい |
| LOVE | 私情と営業の線引きに注意 | 相性は悪いが情がある。感情管理を最優先 |
| BADBOY | 扱えるが気を抜かない。境界線を維持 | 最も要警戒。深追い禁物・黒服相談を検討 |

## 4. F-14 占い・相性診断

### 4.1 目的
客と自分の占い（生年月日等）から**相性**を診断し、その顧客に対して「**気をつけるべきこと**」を提示・選択・保存できるようにする。会話フック（占いの話題）とセルフガイド（地雷回避）の二役を担う。

### 4.2 入力（マスタ設定方針）
入力は **「自分（ユーザー）＝色濃く、相手（顧客）＝任意」** を原則とする。診断は常にユーザー自身の宿命・本質を主軸に置き、相手情報は補助的に重ねる。

- **ユーザー自身の占い基礎情報**（プロフィールに1回登録・**必須情報を厚く**）：
  - 生年月日（**必須**）、出生時刻・出生地（任意・命式精度向上用）、血液型（任意）、性格傾向・過去の大きな出来事（任意・鑑定の深みに反映）。
  - ユーザー情報は診断の**主軸（重み大）**として扱う。
- **顧客の占い基礎情報**（**任意入力・分かる範囲**）：
  - 生年月日（**必須**：本機能を使う最低条件）、血液型・出生時刻・性格傾向等（任意）。
  - 未登録の任意項目は診断から除外し、判明分のみで鑑定する。
- **関係性の選択（選択式・必須）**：診断は関係性の種別によって観点・注意点を出し分ける。以下から選択する（複数選択可）。
  | 関係性 | 主な観点 |
  |---|---|
  | 友人 | 気の合い方・長続きするか |
  | 仕事のパートナー | 金銭・信頼・組んで良いか |
  | 恋愛 | 距離感・依存・惚れ込みの是非 |
  | 客として（営業） | 太客化・接し方・地雷回避 |
  | 家族・その他 | （自由記述で補足） |
- **占い方式の選択（複数可）**：
  | 方式 | 必要入力 | 用途 |
  |---|---|---|
  | 動物占い（個性心理学） | 生年月日 | キャラ理解・会話フック |
  | 星座（西洋占星術） | 生年月日 | 相性・話題 |
  | 干支 | 生年 | 話題・相性の補助 |
  | 血液型 | 血液型 | 会話フック（参考値） |
  | 数秘術（誕生数） | 生年月日 | 性格傾向 |

> **占いロジックは別モジュール（占いエンジン）として別途作成する。** 本書はF-14の入力・出力・業務ルールのみを定義し、スコア算出式・命式計算・鑑定文生成アルゴリズムは占いエンジンの設計に委ねる。エンジンには複数の**鑑定ペルソナ（口調スタイル）**を差し替え可能なプロンプトテンプレートとして持たせる（例：断言型＝細木数子風など）。ペルソナの参考スクリプトは `docs/prompts/占い鑑定ペルソナ_参考.md` に格納する。

### 4.3 出力
1. **相性ランク**：`S / A / B / C / D` の5段階（内部スコア0–100から算出）。
2. **相性サマリ**：関係性の傾向を1〜2文で提示（例：「距離を詰めるほど良くなるタイプ同士」）。
3. **気をつけるべきこと（注意点リスト）**：診断結果に応じた注意点候補を**チェックボックスで提示**。ユーザーが**気になる項目を選択（ピン留め）**でき、選んだ項目は顧客詳細に保存され、接客前・返信案生成前に表示される。
   - 注意点候補の例：「押しすぎると引く」「メンツを立てると機嫌が良い」「話を遮らない」「金銭の話は慎重に」「連絡はマメより間を空ける方が刺さる」「否定されると不機嫌になる」等（方式×相性のマスタから生成）。
4. **会話フック**：「占い好き？実は相性めっちゃ良いらしいよ」等、話題化用の一言案（F-06返信案生成に連携）。

### 4.4 ランク×相性の診断（統合ロジック）
「それぞれの相性で診断可能とする」の要件に対応し、**顧客ランク（F-12）を診断結果に必ず反映**する。相性ランクだけでなく、ランクとの組み合わせで注意点と方針を出し分ける。
| 例 | 出力方針 |
|---|---|
| VVIP × 相性S | 「天性の相性。特別感を演出しつつ、慢心せず記念日を確実に押さえる」 |
| VIP × 相性C | 「相性は普通。会話の型（鉄板ネタ）で安定運用。無理に深掘りしない」 |
| IP × 相性A | 「太客化の最大チャンス。占いを口実に接触頻度を上げる」 |
| LOVE × 相性S | 「のめり込み注意。私情と売上を切り分け、依存し過ぎない」 |
| BADBOY × 相性D | 「地雷確率最大。深追い禁止・境界線を明確に・黒服相談を推奨」 |

### 4.5 業務・倫理ルール（重要）
- 占い結果は**エンタメ・会話補助・自己整理の材料**であり、**顧客の人格や行動を断定するものではない**旨をUIに明示する。
- 相性が悪い・BADBOY判定でも、**顧客を貶める表現や差別的断定は生成しない**（黒服機能の応答方針に準拠）。
- 危険・トラブルの兆候（v1.0 F-02リスクスコア高、ストーカー等）は占いで代替せず、**必ず黒服機能・警察相談導線（#9110）へ誘導**する。占いはリスク判断の代替にしない。
- 占い基礎情報（生年月日等）は顧客の個人情報。v1.0のセキュリティ要件（本人以外アクセス不可・保存時暗号化）に従う。

## 5. データモデル追加（業務レベル）

v1.0の `users/{uid}/customers/{cid}` を拡張する（物理設計は別途）。

```
customers/{cid}
  rank: enum(VVIP|VIP|IP|LOVE|BADBOY)      // F-12 単一ランク（任意・未設定可）
  rankHistory: [{ rank, changedAt, note }]  // ランク変更履歴
  fit: {                                    // F-13 向き不向き
    level: enum(得意|普通|苦手)
    reasonTags: string[]                    // 理由タグ（複数）
    fatigue: enum(低|中|高)                  // 接客後の消耗度
    note: string
  }
  fortune: {                               // F-14 占い基礎情報（相手＝任意）
    birthday?: date                         // 本機能利用には必須（分かる範囲で）
    bloodType?: enum(A|B|O|AB)
    birthTime?: string                      // 任意（命式精度向上）
    traits?: string                         // 任意（性格傾向・過去の出来事メモ）
  }

customers/{cid}/compatibility/{diagId}      // F-14 診断結果（履歴）
  relationshipTypes: string[]               // 選択式：友人|仕事のパートナー|恋愛|客として|家族その他
  persona: string                           // 使用した鑑定ペルソナ（例：assertive_saiki）
  methods: string[]                         // 使用した占い方式
  rankResult: string                        // S|A|B|C|D（関係性ごとに算出可）
  scoresByRelationship: [{ type, score, reason }]  // 関係性別スコア
  summary: string
  cautionCandidates: string[]               // 提示された注意点候補
  pinnedCautions: string[]                  // ユーザーが選択・保存した注意点
  createdAt: timestamp

users/{uid}/profile
  fortuneBase: {                            // 自分の占い基礎情報（主軸＝色濃く）
    birthday: date                          // 必須
    bloodType?: enum
    birthTime?: string
    birthPlace?: string
    traits?: string                         // 性格傾向・過去の大きな出来事
  }
```

**店舗連携（F-15〜F-18）** ※キャスト個人領域とは物理的に別ツリー。店側は下記のみ参照可。

```

stores/{storeId}

    selfReported: { totalSales, ... }        // キャスト自己申告（突合用）※顧客個人情報は含めない
  broadcasts/{bid}                          // F-17 発信
    type(event|birthdayQuota|shift|notice|direct)
    title, body, audience(all|role|castIds[]), targetCastIds?, quota?, eventDate?
    createdBy(role権限者), createdAt
    reads/{uid}  readAt, reaction?
  rankings/{rankId}                         // F-18 ランキング設定と結果
    metric(sales|shimei|dohan|newCustomer|mom), period(day|week|month)
    visibility(public|topN|selfOnly|anonymous|private), n?
    computedAt, entries: [{ castRef, rank, value }]   // 表示は visibility に従う
```

## 8. 店舗連携要件（追加：F-15〜F-18）

### 8.0 位置づけと最重要方針（プライバシー境界）
本追加は、v1.0の前提「個人利用・1ユーザー1アカウント・店舗間共有なし」を拡張し、**店舗（担当黒服・店長）がアプリへ情報を発信でき、売上が店と連動する**マルチロール構成を導入する。ただし以下を**絶対原則**とする。

> **店側（黒服・店長）が閲覧・発信できるのは「店舗運営情報」に限定する。キャストの個人領域 ―― 顧客の個人情報・LINEトーク・黒服相談ログ・占い・向き不向き ―― は店側から一切見えない（v1.0 SEC-02/07を維持）。**

- 店 → キャスト：イベント・ノルマ・ランキング・店公式売上などを**発信**（キャストは受信）。
- キャスト → 店：店へ渡るのは**売上に必要な数値（本数・金額の実績）と勤怠**のみ。顧客の中身は渡さない。
- これにより「店の売上管理・連絡」と「キャスト個人の武器（顧客・占い・相談）」を**同一アプリ内で分離**する。

### 8.1 F-15 店舗・ロール基盤（Store & Roles）
- **エンティティ**：`Store`（店舗）、`Membership`（ユーザー×店舗×ロール）を追加。
- **ロール**：
  | ロール | 権限概要 |
  |---|---|
  | キャスト | 自分の顧客・占い・売上を管理。店発信情報を受信。店へは実績・勤怠のみ送信 |
  | 担当黒服 | 担当キャストへの連絡・ノルマ設定・実績確定。個人領域は不可視 |
  | 店長 | 店全体の発信・ランキング設定・売上確定・メンバー管理。個人領域は不可視 |
- **加入**：キャストは招待コード/リンクで店舗に加入。**複数店舗の掛け持ち・移籍**を許容（v1.0 Open Issue #4を本要件で正式スコープ化）。所属ごとにデータを分離集計。
- **退店**：所属解除後も、キャストの個人領域データは本人手元に残る（店に渡した実績は店側集計に残存）。
- **サーフェス分離（決定）**：**店舗機能はキャストアプリとは独立した「店舗専用コンソール」として提供する**（同一アプリ内のロール切替にはしない）。
  - **キャストアプリ**：キャスト個人が使う。個人領域＋（店舗プラン加入時のみ）店発信の受信・実績送信。
  - **店舗コンソール**：担当黒服・店長が使う管理サーフェス（Web管理画面を想定）。発信・売上確定・ランキング設定・メンバー管理。
  - 両サーフェスは同一バックエンドを共有するが、**店舗コンソールからキャスト個人領域へはアクセス不可**（権限で物理的に遮断）。キャストアプリ側も他キャストの個人領域は見えない。

### 8.2 F-16 店舗売上連動（Store Sales Integration）
顧客の来店金額（F-03）と店舗の売上計上を連動させる。

- **突合モデル（自己申告 × 店確定）**：
  - キャストの来店登録（金額・指名・同伴・場内・ボトル）が、当該キャストの**店売上への貢献**として集計候補になる。
  - 店側（黒服/店長）が**伝票確定額**を入力・確定 → キャストの数値に反映。**店確定額を正**とし、自己申告との差分をキャストへ通知。
  - 店にPOS/表計算がある場合は将来CSV/API連携（Should、初期は手入力/取込）。
- **連動対象**：総売上・指名本数・同伴数・場内・ボトル。
- **F-09/保証カウントダウンへ反映**：目標・逆算ペースは店確定値ベースで表示（確定前は暫定値と明示）。
- **切り分け**：店へ渡すのは金額・本数・卓の実績のみ。**誰の（顧客の）売上かの顧客個人情報は渡さない**（内部IDや匿名ラベルで集計）。

### 8.3 F-17 店舗からの情報発信（お知らせ／ブロードキャスト）
担当黒服・店長がキャストへ情報を発信できる。**発信は店側ロールのみ、キャストは受信・既読・リアクションのみ**。

- **発信コンテンツ種別**：
  | 種別 | 例 |
  |---|---|
  | 看板イベント | 周年・大型イベント・キャンペーンの告知 |
  | バースデーノルマ | キャストの誕生日イベントの売上目標・支援体制 |
  | シフト・ヘルプ要請 | 出勤要請、応援依頼、卓ヘルプ |
  | 全体目標・連絡 | 月間目標、店からの通達 |
  | 個別連絡 | 担当黒服→担当キャストの1:1連絡 |
- **配信範囲**：全店 / ロール指定 / 特定キャスト（個別）。
- **バースデーノルマは F-09 と連動**：発信された目標が自動で目標値に取り込まれ、逆算ペース・進捗を表示。
- **通知**：プッシュ/アプリ内通知、既読管理、締切・イベント日はカレンダー（F-04）に取り込み可。

### 8.4 F-18 店内ランキング（公開/非公開の可変設定）
店長がランキングを設定し、**公開範囲を種別ごとに細かく選べる**。

- **ランキング種別**：総売上 / 指名本数 / 同伴数 / 新規獲得 / 前月比 等。**期間**：日/週/月。
- **公開範囲（店長が種別ごとに設定）**：
  | モード | 内容 |
  |---|---|
  | 全体公開 | 全キャストに順位・源氏名を公開 |
  | 上位N位のみ公開 | TOP N だけ公開、以下は非表示 |
  | 自分の順位のみ | 全体は見せず、各人に自分の順位だけ表示 |
  | 匿名順位 | 源氏名を伏せ、順位と数値の分布のみ公開 |
  | 非公開（店長のみ） | キャストには一切見せない |
- **キャスト配慮**：自分自身の順位・数値は常に本人に見える。過度なプレッシャー/晒しを避けるため、既定はやや控えめ（例：「自分の順位のみ」）を推奨。将来、個人のランキング表示オプトアウトの可否は店ポリシー次第で検討。

### 8.5 F-19 契約・プラン体系（課金モデル）（決定）
課金は **「個人契約」と「店舗契約」を独立（別々）** に設ける。v1.0のみ利用なら個人契約のみ、v1.1の店舗機能を使うなら店舗契約を上乗せする。

| プラン | 契約主体 | 課金 | 使える機能 | サーフェス |
|---|---|---|---|---|
| **個人プラン**（v1.0相当） | キャスト個人 | キャストが支払い | v1.0全機能＋v1.1のキャスト個人機能（F-12ランク／F-13向き不向き／F-14占い） | キャストアプリ |
| **店舗プラン**（v1.1店舗機能アドオン） | 店（店長） | 店が支払い | 上記に加え店舗連携（F-15〜F-18）を所属キャストへ付与＋店舗コンソール | キャストアプリ ＋ 店舗コンソール |

**業務ルール**
- 両契約は**独立して課金・管理**される（一方の解約が他方を止めない）。
- **個人契約のみ**：店舗連携機能（F-15〜F-18）は無効。キャストは個人機能だけを単独で使える。
- **店舗契約あり**：店に所属するキャストへ店舗機能が**プラス（アドオン）**され、店舗コンソールが有効化。
- キャストは個人契約を保持したまま、加入した**店舗ごと**に店舗機能が有効化/無効化される（掛け持ち時は店単位で判定）。
- 店舗契約はキャストの個人契約を代替しない（＝店が契約しても、キャスト個人機能を使うにはキャスト側の個人契約が必要）。※将来「店がキャスト個人分を代理購入/負担」する束ね契約はオプションとして別途検討（本版ではスコープ外）。
- **無料/機能制限**：個人プランのFree枠の有無は要検討（Open Issue）。
